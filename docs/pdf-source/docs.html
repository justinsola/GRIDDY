1.Overview

GRIDDY is a browser-only tool for building grid survey questions and exporting them to Qualtrics. There's no backend or database.

  • Researchers design a grid in the editor and preview it live.
  • Surveys are saved in the browser's localStorage. They can be backed up as JSON.
  • Export produces a .qsf file that Qualtrics imports directly, or a JS snippet to paste.
  • Respondents answer inside Qualtrics. Answers are stored as JSON in embedded-data fields (GridAssignments, or GridPrefills / GridResponses in experimental mode).
Editor (ConfigPanel) → EditorContext (state) → PreviewPanel
                              ↓
          surveysApi → localStorage    qualtricsExport → .qsf / JS → Qualtrics

Stack: React 18, TypeScript, Vite, Tailwind, React Router, Vitest. Hosted on GitHub Pages as static files. Licensed under the MIT License.

2.Using GRIDDY

The editor

Settings on the left, live preview on the right. Pick a category in the Placing row, then click cells to fill them in. Name the survey at the top and click Save.

How respondents answer, and experiments

Section 03 picks the input method. Section 04 turns on experimental mode, where the grid is pre-filled and respondents react to it.

Respondent preview

Shows exactly what respondents will see in Qualtrics. It runs the real exported script, and answers here aren't saved.

My Surveys

Export to Qualtrics

Click Export to Qualtrics, then Download .qsf, and import that file in Qualtrics. The dialog lists the steps and the field the answers are saved to.

Combining several grids into one survey

From My Surveys, click Make multi-question survey. Add saved grids, order them, name each data field, then download one .qsf.

3.The codebase

Data model (src/grid-types.ts)

A survey is a GridConfig with four parts: layout (rows, cols, center cell, barriers), tuning (sizes), survey (categories, selection mode) and optional experimental (pre-filled grid + response labels). Cells are keyed "r{row}-c{col}", 1-based.

State (src/EditorContext.tsx)

One reducer holds the survey being edited. Components read it with useEditor() and change it by dispatching actions such as updateLayout, updateSurvey, setConfig or newSurvey.

Key files

components/ConfigPanel.tsxLeft-hand editor UI
components/PreviewPanel.tsxLive preview and Export modal

lib/qualtricsExport.tsBuilds the Qualtrics JS and .qsf

lib/imageInput.tsCompresses uploaded images into the survey

Adding a new setting

Add it to the type → give it a default in createDefaultConfig and normalizeConfig → add a control in ConfigPanel → render it in PreviewPanel and in qualtricsExport.ts → add a test.

The Qualtrics script is plain JavaScript, not React, so visual features have to be built in both places. Use the respondent preview to check that they match.

4.Building locally

Requires Node 22+ and git. No environment variables are needed.

git clone https://github.com/justinsola/GRIDDY.git
cd GRIDDY
npm install
npm run dev        # http://localhost:5173
CommandDoes
npm run devDev server with hot reload
npm run buildType-check, then bundle to dist/. This is what the Pages deploy runs.
npm run previewServe the built dist/ locally
npm testRun the Vitest tests
npm run lintESLint

Before pushing: run npm run build (and ideally npm test and npm run lint). If it fails locally, the deploy fails too. Unused variables count as build errors.

To see exactly what will be deployed, build with the live site's path and preview it at http://localhost:4173/GRIDDY/:

BASE_PATH=/GRIDDY/ npm run build
npm run preview

Saved surveys are stored per site: localhost and the live site keep separate lists. Use Export/Import JSON to move them.

5.Deploying to GitHub Pages

A GitHub Actions workflow (.github/workflows/pages.yml) publishes the site. Merging to main is the deploy. There's no separate deploy command.

Push to…Result
mainThe workflow builds the app and the live site updates in a minute or two
Any other branch or PROnly the CI checks run. The live site is untouched.

The site is served at https://www.jlsola.com/GRIDDY/: a project site on GitHub Pages lives at the owner's Pages domain plus the repository name. The workflow passes the repository name to the build as BASE_PATH, so renaming the repository moves the site with no code change. Under the repo's Settings → Pages, the source must stay GitHub Actions.

Adding a feature

git switch main && git pull
git switch -c feature/my-change
# ...build it, check npm run build...
git add -A && git commit -m "My change"
git push -u origin feature/my-change
  1. Open a pull request into main on GitHub.
  2. Wait for the green check, CI / Build, test, lint (GitHub Actions). Red means something failed: click Details.
  3. Merge the PR. The live site updates automatically; watch the run under Actions → Deploy to GitHub Pages.

If the live site breaks

  • Via git: git revert <commit> on main and push. The workflow deploys a build without the change.
  • Redeploy the last good build: under Actions → Deploy to GitHub Pages, open the last successful run and choose Re-run all jobs.

Everything needed to deploy lives in this repository and the owner's GitHub account. No third-party dashboard is involved.

6.Keeping it healthy

404.html

The app has client-side routes, so there's no real /history file. GitHub Pages serves 404.html for any path that isn't a real file, and the deploy workflow makes 404.html a copy of index.html, so loading or refreshing any page works. Two pieces of code keep routes and assets on the /GRIDDY/ path: vite.config.ts sets Vite's base from BASE_PATH, and src/main.tsx gives React Router the same path as its basename. Don't hard-code absolute URLs; use router links and relative asset imports.

Checks

npm run build, npm test and npm run lint all pass cleanly on main. GitHub Actions (.github/workflows/ci.yml) runs all three on every PR and every push to main. If one fails, something you changed caused it.

CI installs with npm ci, so when you change dependencies, commit the updated package-lock.json too.
